Raksha — Team Split, Branching & Integration Plan

Goal: two people work in parallel without overwriting each other, while agreeing on contracts early enough that final integration becomes mechanical rather than chaotic.

1. Team Ownership

OwnerPrimary workMust not change casually
YouRaksha Web UI, Core backend, Incident engine, Validation, Evidence, CAP, WhatsApp, Phone, MCP integration.Shared schemas after freeze; portal contracts after integration freeze.
TeammatePortal A + Portal B UIs and backend behavior; CAP client integration; portal-specific states.Core API/schema contracts after freeze.

2. Branch Model

main
 ├── develop (optional integration branch)
 │
 ├── feature/raksha-core
 ├── feature/raksha-web
 ├── feature/raksha-whatsapp
 ├── feature/raksha-phone
 ├── feature/raksha-mcp
 │
 ├── feature/portal-a
 └── feature/portal-b

If two people are the only developers, you can simplify to main + short-lived feature branches. The important rule is that nobody develops directly on main.

3. Freeze the Contract First

Before UI polish or portal polish, commit:

packages/schemas/incident.ts
packages/schemas/cap.ts
packages/schemas/events.ts
packages/cap-sdk/index.ts
docs/cap-contract.md
After this freeze, changes require an explicit team discussion and a version bump.

5. Teammate Branches

feature/portal-a

Cyber Fraud Intake Portal. Build against CAP, not against internal Raksha APIs.

feature/portal-b

Financial Institution Response Console. Consume CAP events and call CAP verification/query methods.

6. Shared Contract Rules

  • Never hardcode endpoint responses in portal code after integration begins.
  • Never change field names locally without updating the shared schema.
  • Use shared TypeScript types or generated types.
  • Use synthetic IDs and data.
  • Every cross-service call requires a correlation/case ID.

7. Local API Contract

Core:
POST /v1/incidents
POST /v1/incidents/:id/evidence
POST /v1/incidents/:id/validate
GET  /v1/incidents/:id

CAP:
GET  /cap/capabilities
POST /cap/cases
POST /cap/actions/validate
POST /cap/actions/execute
GET  /cap/cases/:id
GET  /cap/cases/:id/events
POST /cap/events

8. Portal Integration Contract

Portal A should depend only on CAP:

CAP.execute(
  "report_financial_fraud",
  incident
)

Portal B should depend only on CAP:

CAP.getCase(incidentId)
CAP.execute("acknowledge_response", payload)

9. Git Workflow

# start from updated main
git checkout main
git pull origin main

# create branch
git checkout -b feature/portal-a

# work
git add .
git commit -m "feat(portal-a): add fraud intake"

# push
git push -u origin feature/portal-a

# open PR into main/develop

Use small commits. Avoid “final final latest” commits.

10. Commit Naming

feat(core): add incident state machine
feat(cap): add execute action endpoint
feat(portal-a): add fraud intake flow
feat(portal-b): add response console
feat(web): add evidence review
fix(core): reject conflicting transaction amount
chore(repo): update shared schemas

11. Pull Request Rules

  • One logical feature per PR.
  • Describe API changes explicitly.
  • Include a local test command.
  • Never merge if the shared contract is knowingly broken.
  • At least one teammate reviews cross-cutting changes.

12. Mock Contract Strategy

Before the real backend is complete, publish mock CAP handlers so the teammate can build independently.

portal-a
  ↓
mock CAP client
  ↓
fixture response

Later:
portal-a
  ↓
real CAP client
  ↓
real backend

This allows parallel work without waiting for the backend.

13. Daily Integration Rhythm

MomentAction
Start of dayPull main; rebase/merge if needed.
During workStay on own feature branch.
Contract changeDiscuss before coding against a new structure.
End of featureOpen PR and run local integration test.
End of dayUpdate a simple shared checklist of what works.

14. Integration Order

  1. Merge schemas/CAP types.
  2. Merge Core API.
  3. Merge Portal A against real CAP.
  4. Merge Portal B against real CAP.
  5. Integrate Web.
  6. Integrate WhatsApp.
  7. Integrate Phone.
  8. Integrate MCP.
  9. Run full end-to-end test.

15. Never Merge Everything At Once

Do not wait until the final day and merge five large branches simultaneously.

Instead:

Day 1:
schemas + CAP skeleton

Day 2:
Portal A works with CAP

Day 2:
Portal B works with CAP

Day 3:
Web → Core

Day 3:
Core → CAP

Day 4:
Portal A/B end-to-end

Day 4:
WhatsApp

Day 5:
Phone

Day 5:
MCP

Final:
polish + demo

16. Integration Test

Create one script that exercises the entire system without the UI:

npm run test:e2e:cap

Expected:

1. Create incident
2. Add synthetic evidence
3. Validate
4. Execute report_financial_fraud
5. Portal A creates case
6. incident.accepted event emitted
7. Portal B receives case
8. Portal B acknowledges
9. response.acknowledged emitted
10. Raksha case becomes ACKNOWLEDGED

17. Channel Contract Test

All three user-facing channels must create equivalent canonical incidents for the same synthetic scenario.

WEB INPUT
   └── incident A

WHATSAPP INPUT
   └── incident B

PHONE INPUT
   └── incident C

Normalize:
A == B == C
for equivalent inputs

18. Final Merge Procedure

1. Stop feature work.
2. Pull main.
3. Merge/rebase each branch one at a time.
4. Run typecheck.
5. Run unit tests.
6. Run CAP integration test.
7. Run end-to-end demo.
8. Verify environment variables.
9. Deploy staging.
10. Run end-to-end on staging.
11. Tag the demo release.

19. Staging

Deploy one known-good environment before the final demo. Point all adapters to the staging database and mock portals. Do not have one person's laptop acting as a hidden production dependency.

20. Environment Separation

.env.local        local development
.env.staging      demo environment
production        only if explicitly needed

For the hackathon, staging can effectively be your “production demo.”

22. What To Do If Contracts Need To Change

Do not silently modify them in one branch. Add a versioned schema:

raksha/0.1
raksha/0.2

Update consumer + producer together in one integration PR.

23. Merge Checklist

  • Does the build pass?
  • Does TypeScript typecheck?
  • Do unit tests pass?
  • Does CAP return the documented schema?
  • Can Portal A create a case?
  • Can Portal B consume it?
  • Does the event path work?
  • Does Web create the same incident?
  • Does WhatsApp create the same incident?
  • Does Phone create the same incident?
  • Does MCP invoke the same CAP actions?

24. Communication Rule

Never coordinate by “just changing the backend and telling me later.” All shared contract changes go into the repository and are documented in the PR.

25. Final Team Milestone

The project is integrated only when one synthetic incident can travel:

Phone / WhatsApp / Web
        ↓
Raksha Core
        ↓
CAP
        ↓
Portal A
        ↓
CAP Event
        ↓
Portal B
        ↓
CAP Event
        ↓
Raksha Tracker

and the same CAP action can also be invoked by the MCP test agent.

This collaboration plan intentionally favors simple Git workflows and a small number of shared contracts over complex release engineering.
