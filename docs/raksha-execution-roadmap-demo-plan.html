Raksha — Execution Roadmap, Milestones & Demo Checklist

This document is the practical execution plan for taking the Raksha architecture from empty repository to a reliable hackathon demo. The priority is integration risk, not feature count.

If any layer below CAP is unstable, do not spend time polishing the layer above it.

2. Milestone 0 — Contract Freeze

Deliverables

  • Incident schema.
  • CAP action schema.
  • Event schema.
  • Capability manifest.
  • Portal A actions.
  • Portal B actions.

Exit condition

You and teammate can independently write code against the same interfaces without asking what a field means.

  • Capability registry.

5. Milestone 3 — Portal A

Teammate builds the cybercrime intake portal against CAP.

6. Milestone 4 — Portal B

Portal B listens for incident.accepted, retrieves the case through CAP, and lets an operator acknowledge/update the response.

7. Milestone 5 — Web UI

  • Emergency landing screen.
  • Voice input.
  • Screenshot input.
  • Extraction review.
  • One-question missing-field flow.
  • Evidence capsule.
  • Submit.
  • Case tracker.
  • Developer CAP visualization.

8. Milestone 6 — WhatsApp

Support the minimum viable conversation:

START
→ voice note / text
→ ask for screenshot
→ extract
→ confirm transaction
→ validate
→ submit
→ send reference

Do not build a full conversational assistant.

9. Milestone 7 — Phone

Support:

greeting
→ language selection / detection
→ incident description
→ amount
→ request screenshot/SMS if necessary
→ confirmation
→ handoff
→ reference

For the demo, keep the voice vocabulary narrow and make the fallback path robust.

10. Language Architecture

User language
   ↓
STT / text
   ↓
canonical structured incident
   ↓
English/internal schema
   ↓
result
   ↓
TTS / translated response
   ↓

Do not translate every backend field into multiple languages. Only the conversational boundary needs localization.

11. Milestone 8 — MCP

Implement an AI-agent test client that can:

  • create a financial-fraud incident;
  • add evidence;
  • validate;
  • submit;
  • retrieve status.

It should generate exactly the same backend case as the Web/WhatsApp/Phone routes.

13. Daily Priority Rule

Every day, fix the deepest broken layer before building new surface features.
Bad:
Add animation to web while CAP is broken.

Good:
Fix CAP → verify Portal A → verify Portal B → then polish web.

18. Failure Drills Before Submission

FailureExpected behavior
LLM timeoutShow retry; do not corrupt incident.
Vision extraction wrongUser review prevents automatic submission.
CAP unavailableCase remains HANDOFF_PENDING.
Portal A unavailableNo false acknowledgement.
Portal B unavailablecase remains accepted; response pending.
WhatsApp webhook duplicatesIdempotency key prevents duplicate incidents.
Phone dropsResume by incident ID / callback.

19. Idempotency

Every action should include an idempotency key so retries do not create duplicate reports.

  • Freeze UI components.

24. Final Success Criterion

If a judge can watch one incident enter through voice, move through Raksha, cross CAP into Portal A, trigger Portal B through an event, return to Raksha, and then see an AI agent invoke the same CAP action — the project is successful.

This roadmap is intentionally optimized for a hackathon demonstration rather than production scale.
