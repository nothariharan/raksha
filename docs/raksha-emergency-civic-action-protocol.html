BUILD WHAT MOVES INDIA — RAKSHA ARCHITECTURE / PRODUCT / PROTOCOL SPECIFICATION

Raksha

An Autonomous Emergency Incident Protocol for public services. The first implementation is financial cyber-fraud reporting through India's 1930 / NCRP / CFCFRMS ecosystem. Raksha gives humans an emergency interface built for panic, while defining a machine-readable API/MCP interface that future AI agents can use to perform the same structured public-service action.

1. Core Thesis

Emergency public services are badly matched to human behavior during emergencies. A person who has just lost money is operating under fear, time pressure, incomplete information, poor memory and often low digital literacy.

Raksha changes the interaction model from form completion to incident capture → validation → official handoff → tracking.

The first use case is financial cyber fraud. The citizen speaks naturally and attaches a transaction screenshot or bank SMS. Raksha constructs the structured incident information needed for the official reporting process. AI handles messy input; deterministic infrastructure decides whether the packet is complete and what must happen next.

2. Why Raksha Is Not a GPT Wrapper

Persistent incident

There is a case, schema, evidence, validation state and handoff state.

Deterministic execution

The LLM cannot invent an acknowledgement, official status or bank action.

Multiple interfaces

Phone, WhatsApp, web and AI agents all create the same Incident Packet.

Evidence integrity

Original evidence is preserved with hashes and timestamps.

Government handoff

The product is designed around an official emergency rail rather than replacing it.

Agent interface

The future-facing API/MCP layer exposes a typed public-service action rather than a page to click.

3. Existing Official Rail

The official NCRP/1930 ecosystem already provides the emergency reporting mechanism for financial cyber fraud, and official instructions require transaction and supporting information. MHA has also described API integration between banks and the CFCFRMS module for real-time information exchange and consequent financial actions such as lien marking.

Do not claim a public complaint API exists unless an approved interface is provided. The hackathon prototype should use a synthetic 1930/CFCFRMS gateway. The production architecture should replace that adapter with an officially approved API if one becomes available.

5. Revolutionary Thesis

The long-term argument is not “government needs another API.” India already has APIs. The claim is:

Public services should expose typed, safe actions for both humans and software agents, with the same schema, validation, state and audit semantics.

Today an AI agent that needs to report cyber fraud would be pushed toward browser automation. Raksha demonstrates a better model: the agent invokes a machine-readable civic action while the government-facing adapter handles the execution.

Human → Voice/Web/WhatsApp → Raksha Action Protocol → Government
AI Agent → MCP/REST → Raksha Action Protocol → Government

9. Deterministic Validation

LLM / Vision extraction
        ↓
JSON schema validation
        ↓
1930 reporting requirements
        ↓
+ missing field → one-question prompt
+ contradiction → user confirmation
+ complete → packet READY

Example: voice says ₹50,000 while the bank screenshot says ₹5,000. Raksha must stop and ask which is correct. If the UTR is unreadable, it asks only for the transaction number. It never silently guesses.

10. Evidence Capsule

The Evidence Capsule preserves references to raw evidence and records integrity fingerprints from the moment of capture.

EVIDENCE CAPSULE
Incident: RKS-2026-000821

Original voice      SHA-256: abc...
Screenshot #1       SHA-256: def...
Transcript          SHA-256: ghi...
Captured at         2026-08-24T18:43:02+05:30
Protocol version    raksha/0.1
Events              captured → parsed → validated → submitted
SHA-256 proves integrity against the corresponding hash; do not describe hashing alone as a guarantee of legal admissibility.

11. Privacy and Redaction

Raksha should minimize outgoing evidence. The user may send a screenshot containing unrelated account balances, phone numbers or other personal information. The extraction layer identifies what is actually required, while the handoff layer sends only the minimum necessary structured content and evidence references.

  ├─ transaction details ✓

21. The Agent-Native Government Thesis

The second half of Raksha matters because future personal AI agents will need to do more than answer questions. They will need to execute authorized actions in public systems. A human-facing webpage is a poor machine interface. A typed action contract is safer and easier to validate.

Old model:
AI → browser → click page → read error → retry

Raksha model:
AI → MCP/API → typed civic action → deterministic validation → official handoff
Raksha is therefore both an emergency UX and a reference design for agent-native public services.

22. Security Boundaries

  • Never store real bank passwords, UPI PINs, OTPs or government credentials.
  • Never allow the LLM to call arbitrary endpoints.
  • Every action passes schema and policy validation.
  • Never invent official references or recovery outcomes.
  • High-impact actions require stronger authorization.
  • Evidence is minimized and access-controlled.
  • Browser adapters fail closed when page structure changes.

28. What We Are Actually Claiming

Do not claim that Raksha invented cyber-fraud response, 1930, CFCFRMS, bank integration, APIs or MCP. Those pieces already exist in different forms.

The claim is narrower and stronger: Raksha demonstrates a reusable emergency public-service action protocol where the same structured action can be initiated by a human through voice/web/WhatsApp or by an AI agent through API/MCP, while the same deterministic validation, evidence, state and handoff layer protects both paths.

29. Why This Could Be Bigger Than Raksha

After cyber fraud, the protocol could support other emergency or high-friction public-service actions if approved service contracts become available. Examples include identity theft reporting, unauthorized account activity, emergency document loss, or other public-service incidents.

Those are future extensions, not hackathon scope.

30. Final Product Narrative

When someone loses money, the first thing they should lose is not another hour figuring out a government form.

Raksha turns panic into a structured incident, evidence into an auditable packet, and a human emergency workflow into a machine-readable action. The citizen-facing product solves today's problem. The API/MCP layer points toward a future where AI agents can safely interact with public services through typed actions instead of screen scraping.
