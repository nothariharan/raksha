Raksha: End-to-End System Architecture & Build Plan

Raksha is a multimodal emergency public-service interface for financial cyber-fraud reporting, backed by a deterministic incident engine and a proposed Civic Action Protocol (CAP). Humans can access the same incident workflow through Web, WhatsApp and Phone; future software/AI agents can access it through REST/MCP; two synthetic service portals consume CAP to demonstrate service-layer interoperability.

1. System Goals

  • Convert messy emergency input into one canonical Financial Cyber Fraud Incident.
  • Validate the incident deterministically against the required reporting schema.
  • Preserve evidence references and integrity metadata.
  • Route the validated incident through CAP to two independent synthetic service portals.
  • Expose the same actions to future AI agents through MCP.
  • Keep all channels on one backend and one case state machine.
  • Produce a convincing, deterministic end-to-end demo without using real citizen credentials or unapproved live government systems.

2. Product Boundary

The product has two layers: Raksha is the human emergency experience; CAP is the machine-action and service interoperability layer beneath it.
Human:
Phone / WhatsApp / Web
        ↓
Raksha Core
        ↓
CAP
   ┌────┴─────┐
   ↓          ↓
Portal A    Portal B

Portal A should represent a cyber-fraud intake service. Portal B should represent a financial-institution response console. The two portals should be deliberately different so the demo proves CAP connects independent service actors rather than cloning two copies of the same site.

7. Input Abstraction

Every channel must produce one of the following normalized events.

InputEvent =
  TEXT
  VOICE
  IMAGE
  DOCUMENT
  USER_CONFIRMATION
  USER_CORRECTION

This prevents channel-specific business logic.

8. AI Layer

The LLM/Vision layer does only semantic work:

  • Speech-to-text / text understanding.
  • Entity extraction from narrative.
  • Visual extraction from transaction screenshots.
  • Cross-source reconciliation.
  • Generation of a single clarification question.
  • Plain-language explanation.
LLM cannot directly mark an incident as officially submitted, cannot invent an acknowledgement number, and cannot directly execute arbitrary CAP actions.

9. Deterministic Validation

Candidate incident
      ↓
JSON Schema validation
      ↓
Required-field validator
      ↓
Cross-field consistency
      ↓
Policy checks
      ↓
READY / INCOMPLETE / CONFLICT

Example contradiction: screenshot says ₹5,000 while voice says ₹50,000. Result must be CONFLICT and ask the user to resolve it.

11. Evidence Capsule

Store original synthetic evidence references, SHA-256 hashes, timestamps, source channel, extraction version and processing events. Hashes provide integrity verification; they should not be presented as a guarantee of legal admissibility.

12. CAP Architecture

CAP is the stable service boundary. Portals should not know about Raksha's internal LLM implementation.

CAP
├── Capability Registry
├── Action Router
├── Schema Registry
├── Policy / Authorization
├── Event Publisher
├── Event Subscriber
└── Case Reference Mapping

Minimum CAP operations

GET  /cap/capabilities
POST /cap/cases
POST /cap/actions/validate
POST /cap/actions/execute
GET  /cap/cases/:id
GET  /cap/cases/:id/events
POST /cap/events

13. Portal A — Cyber Fraud Intake

Portal A should expose a realistic but deliberately narrow set of capabilities.

report_financial_fraud
attach_evidence
get_case
get_case_status

It receives the CAP incident, validates required values again at the service boundary, creates its local case, then emits:

incident.accepted

14. Portal B — Financial Institution Response

Portal B should look like an operations console rather than another citizen portal.

get_incident
verify_transaction
acknowledge_response
update_response
get_response_status

Portal B subscribes to incident.accepted. It then gets the incident using CAP, displays it to an operator and emits a response event.

25. Security

  • Synthetic identities only.
  • No real banking credentials.
  • No real OTP/PIN/password storage.
  • CAP actions are allowlisted.
  • High-impact actions require explicit confirmation.
  • Adapters fail closed.
  • Every action has a case/correlation ID.
  • Webhooks are authenticated where practical.

29. Demo Sequence

  1. Citizen uses voice and screenshot in Raksha.
  2. Raksha extracts incident details.
  3. Validator catches or confirms completeness.
  4. Evidence capsule is created.
  5. CAP submits to Portal A.
  6. Portal A emits incident.accepted.
  7. Portal B receives the event and loads the incident via CAP.
  8. Portal B acknowledges/updates it.
  9. Raksha receives the response event.
  10. Switch to developer view: show the same CAP calls invoked by an MCP agent.

32. The Architectural Principle

Channels change. Government services change. AI models change. The canonical incident, CAP contract, policy engine and case state machine should not.
This is a hackathon architecture. CAP endpoints and protocol schemas are proposed interfaces, not claims about existing government APIs. Live government integration should only be used where an approved sandbox/official API is available.
